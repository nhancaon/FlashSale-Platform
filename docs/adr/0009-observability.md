# ADR 0009: Observability (metrics, dashboards, tracing)

Status: accepted (Phase 6)

## Context
We compare Go and Java services and need to see where time goes under load: requests, errors, latency, database pool,
GC and memory, and a request's path across four services.

## Decision
**Metrics (Prometheus, 5 s scrape).** Every service exposes `/metrics` on its container port 8080.
- RED: Go services expose `http_requests_total{method,route,status}` and `http_request_duration_seconds`; Java services
  expose Micrometer's `http_server_requests_seconds_*`, with histogram buckets enabled
  (`management.metrics.distribution.percentiles-histogram.http.server.requests=true`) so p95/p99 work. The names differ
  by runtime, so each RED panel has one query per runtime.
- Runtime: Go services register the Go and process collectors (`go_goroutines`, `go_gc_duration_seconds`,
  `go_memstats_*`, `process_*`); the JVM and Hikari metrics come with Micrometer.
- Business: `inventory_reserve_total{result}` (same name and label in Go and Java), `order_requests_total{result}`,
  `outbox_pending_events` (relay lag), `notification_processed_total{result}`, `gateway_ratelimit_rejected_total{scope}`,
  circuit breaker state (`gateway_upstream_breaker_state`, `resilience4j_circuitbreaker_state`).
- The scaled `outbox-worker` is found with DNS service discovery (the service name resolves to every replica).

**Dashboard.** `deploy/compose/grafana/dashboards/flashsale.json` is generated by `scripts/gen-dashboard.mjs` and provisioned
at startup (no clicking). Rows: status, RED, flash sale, outbox and notifications, resilience, resources.
`scripts/check-dashboard.mjs` runs every query against Prometheus: it caught nothing malformed, and the only empty panels
were legitimately empty (no 5xx errors, rate limiter services not running).

**Tracing (OpenTelemetry to Jaeger).** W3C `traceparent` everywhere.
- Go (gateway, inventory-go): `otelhttp` on the server and on the gateway's upstream transport, plus a span per Oracle
  transaction (`oracle.tx`). Server spans are named `METHOD /first/two` so ids in paths do not blow up cardinality; probes
  and `/metrics` are not traced.
- Java (order, inventory-java, ratelimiter-java): the OpenTelemetry Java agent, attached through `JAVA_TOOL_OPTIONS`, giving
  HTTP, JDBC and JDK `HttpClient` spans without code changes (the saga's calls to inventory propagate the trace).
- Sampling uses the standard `OTEL_TRACES_SAMPLER(_ARG)`; setting `OTEL_ENDPOINT=` and `JAVA_TRACING_OPTS=` (empty) turns tracing
  off, which the benchmarks do so tracing overhead is not part of the measurement.

## Verified
`scripts/check-tracing.sh`: one order through the gateway gives one trace with gateway, order and inventory-go spans
(`POST /api/orders` > `POST /v1/orders` > JDBC inserts + outbox insert > inventory `POST /v1/inventory` > `oracle.tx`).
`scripts/check-dashboard.mjs`: every dashboard query is valid and returns data when the services run.

## Limits
- No exporters for Oracle, Redis, Kafka or the host: database pool metrics come from the services, not from Oracle itself,
  and CPU is per process (`process_cpu_seconds_total`), not per container (no cAdvisor).
- No log aggregation (Loki is optional in the spec): logs are JSON on stdout with `request_id` for correlation.
- Java agent version is "latest" at image build time (not pinned).
