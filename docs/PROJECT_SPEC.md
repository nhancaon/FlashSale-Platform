# FlashSale Platform — Project Spec

> File này là ngữ cảnh cho Claude Code. Làm **từng phase một**, mỗi phase xong phải chạy được và có test. Không tự ý làm trước phase sau.

## 0. Mục tiêu

Xây hệ thống **flash sale** (bán hàng giới hạn, tải đột biến) để:
1. So sánh **Go vs Java** trên cùng một API contract (throughput, latency p95/p99, memory, startup, image size).
2. Áp dụng nhiều design pattern thực tế (rate limit, circuit breaker, outbox, saga, idempotency, worker pool...).
3. Dùng **Oracle DB** làm source of truth.
4. Có đủ phần hạ tầng để apply fresher **Go / Java / DevOps**: Docker, CI/CD, Ansible, k3s, Prometheus/Grafana, k6.

Tiêu chí thành công (phải chứng minh bằng test + báo cáo):
- Sau load test lớn: **không oversell**, tổng tồn kho + tổng đã bán = tổng ban đầu.
- Retry cùng Idempotency-Key **không tạo đơn/trừ kho hai lần**.
- Có báo cáo benchmark Go vs Java trung thực kèm biểu đồ.
- `docker compose up` chạy cả hệ thống; `ansible-playbook site.yml` dựng được trên VM.

## 2. Kiến trúc

```
Client → Gateway (Go) → Order Service (Java) → Inventory Service (Go | Java, đổi được)
                              │                         │
                              └──────── Oracle ─────────┘
                              │
                        outbox_events
                              ↓
                  Outbox Worker (Go) → Kafka → Notification (Go)
Redis: rate limit, cache tồn kho, distributed lock (tuỳ chọn)
```

Services:

| Service | Ngôn ngữ | Vai trò |
|---|---|---|
| `gateway` | Go | Auth JWT, rate limit, routing, circuit breaker, request id |
| `ratelimiter-go` / `ratelimiter-java` | Go + Java | Rate limit service độc lập (cùng contract) + thư viện dùng trong gateway |
| `inventory-go` / `inventory-java` | Go + Java | Giữ/nhả hàng, chống oversell, cùng API contract, cùng schema |
| `order` | Java | Tạo đơn, idempotency, ghi outbox, saga đơn giản |
| `outbox-worker` | Go | Worker pool đọc outbox (`SKIP LOCKED`) đẩy lên Kafka |
| `notification` | Go | Consumer Kafka, giả lập gửi email/SMS |
| `loadtest` | k6 | Kịch bản flash sale |

Quy tắc: `inventory-go` và `inventory-java` **dùng chung một bảng, một contract, một bộ test hợp đồng (contract test)**. Order gọi inventory qua biến môi trường `INVENTORY_URL`.

## 4. Database schema (Oracle)

```sql
CREATE TABLE product (
  id          NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  sku         VARCHAR2(64) NOT NULL UNIQUE,
  name        VARCHAR2(255) NOT NULL,
  price       NUMBER(18,2) NOT NULL
);

CREATE TABLE stock (
  product_id  NUMBER PRIMARY KEY REFERENCES product(id),
  available   NUMBER(10) NOT NULL CHECK (available >= 0),
  reserved    NUMBER(10) DEFAULT 0 NOT NULL CHECK (reserved >= 0),
  version     NUMBER(10) DEFAULT 0 NOT NULL
);

CREATE TABLE reservation (
  id            VARCHAR2(64) PRIMARY KEY,           -- UUID
  order_id      VARCHAR2(64) NOT NULL,
  product_id    NUMBER NOT NULL REFERENCES product(id),
  qty           NUMBER(10) NOT NULL,
  status        VARCHAR2(16) NOT NULL,              -- RESERVED | RELEASED | CONFIRMED
  created_at    TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT uq_reservation UNIQUE (order_id, product_id)
);

CREATE TABLE orders (
  id               VARCHAR2(64) PRIMARY KEY,
  user_id          VARCHAR2(64) NOT NULL,
  status           VARCHAR2(16) NOT NULL,           -- PENDING | CONFIRMED | FAILED | CANCELLED
  total            NUMBER(18,2) NOT NULL,
  idempotency_key  VARCHAR2(128) NOT NULL,
  created_at       TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
  CONSTRAINT uq_order_idem UNIQUE (user_id, idempotency_key)
);

CREATE TABLE order_item (
  order_id    VARCHAR2(64) NOT NULL REFERENCES orders(id),
  product_id  NUMBER NOT NULL REFERENCES product(id),
  qty         NUMBER(10) NOT NULL,
  price       NUMBER(18,2) NOT NULL,
  PRIMARY KEY (order_id, product_id)
);

CREATE TABLE outbox_events (
  id            NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  aggregate_id  VARCHAR2(64) NOT NULL,
  event_type    VARCHAR2(64) NOT NULL,
  payload       CLOB NOT NULL,
  status        VARCHAR2(16) DEFAULT 'NEW' NOT NULL, -- NEW | SENT | FAILED
  attempts      NUMBER(5) DEFAULT 0 NOT NULL,
  created_at    TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL,
  sent_at       TIMESTAMP
);
CREATE INDEX ix_outbox_status ON outbox_events(status, id);
```

Lưu ý Oracle: chuỗi rỗng = NULL, mặc định READ COMMITTED, phân trang dùng `OFFSET ... FETCH NEXT`, luôn dùng bind variable.

## 5. API contract

Mọi request có `X-Request-Id`. Lỗi trả JSON: `{"code":"OUT_OF_STOCK","message":"..."}`.

**Inventory** (`inventory-go` và `inventory-java` giống hệt nhau)
- `GET  /v1/inventory/{sku}` → `{sku, available, reserved}`
- `POST /v1/inventory/reserve` body `{orderId, sku, qty}` → 200 `{reservationId}` | 409 `OUT_OF_STOCK`. Idempotent theo `(orderId, sku)`.
- `POST /v1/inventory/release` body `{orderId, sku}` → 200 (idempotent)
- `POST /v1/inventory/confirm` body `{orderId, sku}` → 200
- `GET  /healthz`, `/readyz`, `/metrics`
- Chiến lược chống oversell chọn bằng env `STOCK_STRATEGY`:
  - `atomic` : `UPDATE stock SET available = available - :n, reserved = reserved + :n WHERE product_id = :id AND available >= :n` (kiểm tra rows affected)
  - `pessimistic` : `SELECT ... FOR UPDATE` rồi update
  - `optimistic` : so sánh `version`, retry có giới hạn

**Order**
- `POST /v1/orders` header `Idempotency-Key` (bắt buộc), body `{items:[{sku,qty}]}` → 201 | 409 | 200 (replay cùng key trả lại kết quả cũ)
- `GET /v1/orders/{id}`

**Rate limiter**
- `POST /v1/check` body `{key, limit, windowSec}` → `{allowed, remaining, retryAfterMs}`
- Thuật toán chọn bằng env: `token_bucket`, `sliding_window`, `fixed_window` (Strategy pattern), lưu state trong Redis bằng Lua script (atomic).

**Gateway**: `/auth/login` (JWT giả lập), proxy `/api/*`; rate limit theo user + IP; trả 429 kèm `Retry-After`.

## 6. Design pattern phải có (và chỗ áp dụng)

| Pattern | Ở đâu |
|---|---|
| Strategy | Thuật toán rate limit; chiến lược trừ kho |
| Chain of Responsibility / Decorator | Middleware gateway (auth → ratelimit → logging → proxy) |
| Circuit Breaker + Timeout + Retry (backoff + jitter) + Bulkhead | Order → Inventory, Gateway → Order |
| Idempotency Key | Order, reserve/release |
| Transactional Outbox | Order ghi `outbox_events` cùng transaction với `orders` |
| Worker Pool / Producer-Consumer | `outbox-worker` (Go), dùng `FOR UPDATE SKIP LOCKED` |
| Saga (orchestration) | Order: reserve → (giả lập payment) → confirm; lỗi → release |
| Cache-aside | Cache `GET inventory` trong Redis, invalidate khi thay đổi |
| Repository | Truy cập DB ở cả Go và Java |
| Factory | Tạo strategy từ config |
| Observer / Pub-Sub | Kafka consumer notification |

Mỗi pattern chính cần 1 file ADR ngắn trong `docs/adr/` (bối cảnh, quyết định, đánh đổi).

## 7. Các phase (làm tuần tự)

### Phase 0 — Khung repo
- Tạo cấu trúc thư mục, `Makefile`, `.editorconfig`, `.gitignore`, `CLAUDE.md`, README khung.
- `deploy/compose/docker-compose.yml`: Oracle, Redis, Kafka, Prometheus, Grafana (chưa có app).
- Migration V1 theo schema mục 4, seed vài product + stock.
- **Xong khi**: `make up` chạy, `make db-migrate` tạo bảng, kết nối được Oracle.

### Phase 1 — Rate Limiter (Go + Java)
- 3 thuật toán qua Strategy, state trong Redis + Lua script.
- Cùng API `/v1/check`, cùng metrics Prometheus (`ratelimit_allowed_total`, `ratelimit_rejected_total`, latency histogram).
- Unit test từng thuật toán (có test thời gian bằng clock giả), integration test với Testcontainers Redis.
- Concurrency test: 1000 goroutine/thread cùng key, số request được cho phép không vượt limit.
- **Xong khi**: test pass, `go test -race` sạch, benchmark sơ bộ (k6 hoặc wrk) lưu ở `loadtest/results/`.

### Phase 2 — Inventory (Go + Java)
- Implement đủ 3 chiến lược `STOCK_STRATEGY`, idempotent reserve/release/confirm.
- Connection pool cấu hình bằng env (HikariCP / `database/sql`). Map lỗi `ORA-00001`, `ORA-00060`, timeout sang mã lỗi có nghĩa.
- Cache-aside cho `GET`.
- `contract-tests/`: một bộ test chạy được vào cả hai service qua `BASE_URL`.
- Test oversell: 100 hàng, 2000 request đồng thời → đúng 100 thành công, `available = 0`, không âm.
- **Xong khi**: cả hai service pass cùng contract test; có bảng so sánh latency 3 chiến lược × 2 ngôn ngữ.

### Phase 3 — Order service (Java)
- Tạo đơn với Idempotency-Key (unique constraint, bắt `ORA-00001` để trả lại kết quả cũ).
- Saga: reserve → confirm; lỗi thì release; ghi `outbox_events` trong cùng transaction.
- Resilience4j: circuit breaker, retry, timeout, bulkhead khi gọi inventory.
- Test: giả lập inventory chậm/lỗi → breaker mở, không cạn thread; gửi 2 lần cùng key → chỉ 1 đơn.
- **Xong khi**: end-to-end tạo đơn qua Compose chạy đúng, test chaos đơn giản pass.

### Phase 4 — Outbox worker + Notification (Go)
- Worker pool N goroutine, `SELECT ... FOR UPDATE SKIP LOCKED`, publish Kafka, đánh dấu `SENT`, retry có backoff, quá số lần thì `FAILED`.
- Notification consume Kafka, xử lý idempotent theo event id.
- Graceful shutdown bằng `context`.
- Test: chạy 3 worker song song, mỗi event gửi đúng 1 lần; tắt worker giữa chừng không mất event.

### Phase 5 — Gateway (Go)
- Middleware chain: request id → logging → JWT → rate limit (gọi ratelimiter hoặc thư viện nội bộ) → circuit breaker → reverse proxy.
- Trả 429 + `Retry-After`; health aggregation.
- Test middleware độc lập và test tích hợp.

### Phase 6 — Observability + Load test + Báo cáo
- Metrics chuẩn cho mọi service (RED: rate, errors, duration; pool usage; GC/goroutine/JVM).
- Grafana dashboard JSON lưu trong repo (provisioned).
- OpenTelemetry tracing xuyên gateway → order → inventory.
- k6: kịch bản flash sale (ramp lên 2–5k VU, 100 tồn kho), threshold `p95 < X ms`, `http_req_failed < Y%`.
- Script **reconcile** sau test: tổng available + đã bán = ban đầu, không order trùng.
- Chạy cùng kịch bản cho 2 biến thể (inventory-go vs inventory-java) trên cùng máy, cùng giới hạn CPU/RAM container; lặp ≥ 3 lần.
- Viết `docs/benchmark-report.md`: phương pháp, bảng số liệu, biểu đồ, kết luận trung thực (kể cả chỗ Java thắng), hạn chế (Oracle Free, máy cá nhân).

### Phase 7 — CI/CD
GitHub Actions:
- `ci-java`, `ci-go`: build, test (Testcontainers), lint (`golangci-lint`, Checkstyle/Spotless), coverage.
- `docker`: multi-stage Dockerfile, non-root, build + push GHCR, so sánh image size Go vs Java trong summary.
- `security`: Trivy scan image, Dependabot.
- `ansible-lint` + `ansible-playbook --check`.
- `loadtest` (manual hoặc nightly): chạy k6 smoke, fail nếu vượt threshold.

### Phase 8 — Ansible + k3s
- Dựng 2–3 VM local (Vagrant hoặc Multipass) hoặc VPS.
- Roles: `common` (user non-root, tắt root SSH, ufw, node_exporter), `docker`, `oracle` (container), `redis_kafka`, `monitoring`, `k3s` (server + agent), `app_deploy`.
- Ansible Vault cho mật khẩu Oracle, JWT secret.
- Rolling deploy với `serial: 1`.
- Manifest k8s: Deployment, Service, ConfigMap, Secret, probes, resource requests/limits, **HPA** theo CPU.
- **Xong khi**: `ansible-playbook -i inventory/dev.ini site.yml` dựng từ máy trống; chạy lần hai không có `changed` (idempotent); k6 bắn tải thì HPA tăng pod, chụp được dashboard.

## 12. PHỤ LỤC A — Concurrency Lab: so sánh thread/concurrency/code Go vs Java

Thêm thư mục `labs/concurrency-lab/` với hai phần `go/` và `java/` làm **cùng một bộ thí nghiệm**, cùng tham số, cùng format kết quả (JSON/CSV) để vẽ biểu đồ. Làm sau Phase 2, trước Phase 6. Kết quả đưa vào `docs/concurrency-comparison.md`.

### Thí nghiệm bắt buộc

| # | Thí nghiệm | Go | Java (JDK 25) | Đo gì |
|---|---|---|---|---|
| 1 | Tạo N task đồng thời (N = 1k, 10k, 100k, 1M) mỗi task sleep 100ms | goroutine | platform thread, virtual thread | thời gian, RAM đỉnh, có crash/OOM không |
| 2 | Worker pool xử lý M job CPU-bound | goroutine + channel | `ExecutorService` fixed pool, `ForkJoinPool` | throughput, CPU utilization |
| 3 | Fan-out I/O: gọi 10k request giả lập latency 50–200ms | goroutine + `WaitGroup`/`errgroup` | virtual threads, `CompletableFuture` | tổng thời gian, p99 |
| 4 | Bộ đếm dùng chung, 100 luồng × 1M lần tăng | `sync.Mutex`, `atomic`, channel | `synchronized`, `ReentrantLock`, `AtomicLong`, `LongAdder` | thời gian, độ chính xác |
| 5 | Race condition có chủ đích rồi sửa | `go test -race` | jcstress hoặc test lặp + phân tích | cách phát hiện, độ dễ dùng |
| 6 | Producer–Consumer với hàng đợi giới hạn (backpressure) | buffered channel | `BlockingQueue` | throughput, hành vi khi đầy |
| 7 | Cancellation và timeout lan truyền | `context.Context` | `Future.cancel`, interrupt, `StructuredTaskScope` (kiểm tra trạng thái preview theo phiên bản JDK) | task có dừng sạch không, rò rỉ |
| 8 | Deadlock và leak có chủ đích | pprof goroutine dump | `jstack`, JFR | cách chẩn đoán, thời gian tìm ra lỗi |
| 9 | Pipeline nhiều stage (parse → transform → write) | channel pipeline | `Stream`/queue/virtual threads | độ dài code, throughput |
| 10 | Rate limiter cài ở cả hai ngôn ngữ | — | — | số dòng code, số dòng test, độ rõ ràng |

### Nguyên tắc đo đạc
- Cùng máy, cùng giới hạn CPU/RAM (container với `--cpus`, `--memory`), warm-up trước khi đo, lặp ≥ 5 lần, báo trung vị và độ lệch.
- Java dùng JMH cho microbenchmark; Go dùng `testing.B` + `benchstat`.
- Ghi lại phiên bản Go, JDK, flag GC (`GOGC`, `GOMAXPROCS`, `-XX:+UseZGC`...).
- Profiling: Go `pprof` + `go tool trace`; Java JFR + async-profiler. Chụp flame graph cho thí nghiệm 2 và 3.
- Đếm LOC và độ phức tạp bằng `scc` hoặc `cloc` cho từng thí nghiệm, đưa vào bảng.

### Phần "so sánh code" trong báo cáo
Mỗi thí nghiệm có một mục gồm: đoạn code Go và Java đặt cạnh nhau, số dòng, khái niệm cần biết (ví dụ happens-before, memory model, scheduler M:N vs luồng OS/ carrier thread), bẫy thường gặp (goroutine leak, pinning của virtual thread (từ JDK 24 `synchronized` không còn pin carrier thread như JDK 21; vẫn còn với native frame/`synchronized` trong một số trường hợp, nên đo lại thay vì giả định, và so sánh với JDK 21 nếu có thời gian), đóng channel hai lần, `ThreadLocal` với virtual thread), và kết luận "khi nào chọn cái nào".
